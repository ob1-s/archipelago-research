# Carrier and tool boundary

The declared carrier store exposes only enumerate, signed write, finalize/hash, lineage-scoped read, signed read attribution, and provenance inspection. Carrier IDs are opaque safe identifiers; path traversal is rejected. Allowed classes are exactly `DECLARED_LINEAGE_CARRIER` and `DECLARED_BACKUP`.

Every record contains WHO, WHAT, logical WHEN, GENERATION, LINEAGE, content HASH, WRITE AUTHORITY, READ BY, PARENTAGE, carrier class, and the exact write/read capability hashes. Each capability binds one attempt, actor, lifecycle, lineage, generation, carrier ID/class, and exactly one of read or write. The actor-signed write binds the carrier ID, class, lineage, generation, content hash, and exact lowercase-SHA-256 parent set, preventing the controller from relabeling signed bytes as another carrier. A predecessor cannot create a new write after revocation; a successor may read only through its frozen assignment grant and must sign the exact carrier/provenance binding at a later generation.

Content is written with exclusive creation and fsync; metadata is atomically replaced and fsynced. A root-level interprocess lock serializes reload/write/finalize/read-attribution transactions so independent controller instances cannot overwrite one another's logical time or provenance. On restart, metadata, signatures, and exact scheduled writer/read capability attributions are validated before carrier bytes are opened. This prevents a validly signed carrier from an unscheduled writer being substituted after restart. Same-ID/same-content/provenance replay is idempotent; a changed hash, actor, class, capability, or provenance is rejected. An orphaned content file after a crash can only be recovered by a same-hash authorized retry and cannot be overwritten with different content. Carrier roots and artifacts must be real regular filesystem objects: root/content/metadata/lock symlinks and multiply linked artifacts fail closed. Caller-owned roots are not deleted on close.

The carrier store is outside disposable actor mounts and transports bytes over the narrow local actor protocol. It is not general filesystem access. Reads require an active exact recipient before the content path is entered, and the normal orchestrator delivery API returns metadata rather than raw bytes. The controller cannot transform content or relabel its carrier metadata without invalidating the actor signature or capability binding.

Actor tool inventory is empty. The trusted worker exposes no shell command, browser, MCP/plugin endpoint, external database credential, general subprocess interface, or unrestricted network. Read-only runtime binaries present under `/usr` are not exposed as actor commands; arbitrary hostile-code containment is outside this worker-protocol claim. The provider gateway is a separate orchestrator-only component; an OS egress allowlist for the one pinned endpoint is recommended defense-in-depth for deployments, but is neither a validity prerequisite nor an execution blocker under this qualification's stated threat model. Code-level HTTPS/policy pinning alone is not treated as equivalent to network confinement.
